# Только Kafka + CDC: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Убрать gRPC/REST, перевести проект на viper/cobra/easyjson и добавить CDC-джобу TigerBeetle → Kafka по образцу официальной AMQP-джобы.

**Architecture:** Проект становится чисто кафковым. Две джобы поверх одного TigerBeetle-клиента: **sink** (Kafka → TigerBeetle, уже есть) и **cdc** (TigerBeetle → Kafka, новое). Командная строка на cobra, конфиг на viper, горячий JSON на easyjson.

## Global Constraints

- Модуль `github.com/Mi7teR/kafka-tb`, Go 1.25+, `CGO_ENABLED=1`.
- **macOS:** только через `make` — Makefile подставляет `-ldflags=-extldflags=-Wl,-ld_classic`.
- Суммы — строки и `big.Int`. `float64` для денег запрещён.
- **Строгость конфига не ослабляется.** Сейчас `yaml.v3` с `KnownFields(true)` роняет старт на неизвестном ключе. Viper по умолчанию неизвестные ключи игнорирует — опечатка молча возьмёт дефолт. Строгость восстановить явно.
- **Строгость декодера не ослабляется.** easyjson генерировать с `-disallow_unknown_fields`; опечатка в поле сообщения обязана остаться poison.
- `make test`, `make integration`, `golangci-lint run` — зелёные на каждом коммите.
- Conventional Commits.

### Task 22: viper и cobra

**Требования:**

- **cobra:** подкоманды вместо `--mode`. `kafkatb sink` — только консьюмер; `kafkatb cdc` — только CDC-джоба; `kafkatb run` — обе в одном процессе. Общий флаг `--config`. Флаги перекрывают конфиг, конфиг перекрывает дефолты.
- **viper:** чтение yaml + переменные окружения `KAFKATB_*` (сейчас это руками написанный `applyEnv` — заменить), плюс дефолты.
- **Строгость обязательна.** После чтения сверить фактический набор ключей файла с известными и упасть на неизвестном, с указанием ключа. Без этого опечатка в ключе тихо берёт дефолт — ровно тот класс дефекта, что уже ловили в REST-двери.
- Вся существующая валидация значений сохраняется дословно: границы `max_batch_size`, дубликаты ledger/code, адреса TigerBeetle только IP или голый порт, `max_in_flight_per_partition` против потолка, и прочее. Ни одна проверка не теряется.

**Тесты:** каждая существующая проверка конфига остаётся и остаётся падающей на плохом входе; неизвестный ключ в файле — ошибка старта; `KAFKATB_*` перекрывает файл; флаг перекрывает `KAFKATB_*`; каждая подкоманда стартует и гасится по SIGTERM.

### Task 23: easyjson на горячем пути

**Требования:**

- Кодогенерация через `go:generate`, бинарь ставится `go install github.com/mailru/easyjson/...@latest`, цель `generate` в Makefile. Сгенерированные файлы коммитятся.
- **Обязательно `-disallow_unknown_fields`.** Иначе опечатка в имени поля перестанет быть poison и молча даст нулевое значение — свойство, за которое в проекте уже заплачено дважды.
- Перевести: декодер сообщений `internal/codec/jsonc`, тело results-топика `internal/emit`, тело CDC-сообщения (Task 24).
- Замерить до/после на `BenchmarkDecodeJSON` и записать. **Ожидание умеренное:** декодинг сейчас ~2 мкс из ~60 мкс на запись, то есть ~1-3%. Если выигрыш в пределах шума — записать это честно, а не подгонять вывод.

**Тесты:** весь существующий набор `internal/codec/jsonc`, включая фаззинг и всю таблицу poison, зелёный без правок семантики. Отдельный тест: неизвестное поле — ошибка.

### Task 24: CDC-джоба TigerBeetle → Kafka

Аналог официальной `tigerbeetle amqp`, но в Kafka.

**Источник:** `Client.GetChangeEvents(ChangeEventsFilter{TimestampMin, TimestampMax, Limit})`. В Go-клиенте помечен экспериментальным — обращаться через узкий интерфейс, чтобы смена сигнатуры не разошлась по коду.

**Поля `ChangeEvent`:** `Type` (`single_phase`/`two_phase_pending`/`two_phase_posted`/`two_phase_voided`/`two_phase_expired`), `Timestamp`, `Ledger`, все поля перевода, и снимок **обоих счетов на момент события** — балансы, user_data, code, flags, timestamp.

**Формат сообщения** — скелет официального, значения по контракту этого проекта:

```json
{
  "type": "single_phase",
  "timestamp": "1745328372192037030",
  "ledger": "USD",
  "transfer": {"id": "...", "amount": "12.34", "code": "payment", "flags": [...], ...},
  "debit_account":  {"id": "...", "debits_posted": "1250.00", ..., "code": "customer", "flags": [...]},
  "credit_account": {"id": "...", ...}
}
```
`ledger` и `code` — словами из справочников, суммы — десятичными строками по scale, id — UUID-строки, флаги — списком имён. То есть ровно то же, что принимает sink: один контракт на вход и на выход. Несовместимо с официальным потребителем — это осознанный выбор.

**Заголовки Kafka** по образцу официальных: `event_type`, `ledger`, `transfer_code`, `debit_account_code`, `credit_account_code`, `timestamp`.

**Ключ сообщения** — конфигом `cdc.partition_key`: `debit_account_id` (дефолт), `credit_account_id`, `ledger`, `transfer_id`. Ключ определяет, какой порядок видит потребитель, и это его осознанный выбор.

**Прогресс — без внешнего состояния, как у официальной джобы.** На старте прочитать хвост выходного топика по всем партициям, взять максимальный `timestamp` из тел сообщений, продолжить с `timestamp+1`. Флаг `--timestamp-last` перекрывает (в том числе `0` — переиграть всё). Пустой топик — начать с нуля.

**Гарантия — at-least-once**, как у официальной. Дедупликация на потребителе по `timestamp`, который в TigerBeetle уникален и монотонен. Публикация подтверждается до сдвига курсора: потерять событие нельзя, продублировать при падении — можно.

**Цикл:** запрос окна событий → публикация → ожидание ack → сдвиг курсора → следующее окно. Пустой ответ — пауза `cdc.poll_interval` и повтор. Размер окна `cdc.batch_size`.

**Тесты:**
- Пустой топик → старт с нуля; непустой → продолжение с максимального timestamp, без дублей и без пропусков.
- Падение между публикацией и сдвигом курсора → повтор публикации, потребитель видит дубль, но не пропуск.
- Все пять типов событий сериализуются корректно, включая два снимка счетов.
- Неизвестный ledger или code в событии — не молчаливый пропуск: сообщение уходит с числовым значением и предупреждением в лог, событие не теряется.
- Ключ партиционирования соответствует конфигу.

### Task 25: Интеграция CDC

В существующем харнессе: применить проводки через sink, поднять CDC, проверить что события появились в выходном топике, что тела соответствуют применённым проводкам, и что перезапуск CDC не дублирует и не теряет. Плюс двухфазный сценарий: pending → posted даёт два события правильных типов.

## Definition of Done

- gRPC/REST и их зависимости отсутствуют в `go.mod`.
- `kafkatb sink`, `kafkatb cdc`, `kafkatb run` работают и гасятся по SIGTERM.
- Неизвестный ключ конфига и неизвестное поле сообщения — обе ошибки сохранены и покрыты тестами.
- CDC переживает перезапуск без потерь, что доказано интеграционным тестом, а не рассуждением.
