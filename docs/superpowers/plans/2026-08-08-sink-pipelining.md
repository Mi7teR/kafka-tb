# Пайплайнинг синка: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Поднять пропускную способность синка с ~50-70 transfers/сек до тысяч, наполнив батчи TigerBeetle реальным количеством событий.

**Замеры на текущем коде** (`.superpowers/sdd/perf-baseline.md`, 3000 записей, реальный стенд):

| Стадия | p50 | Доля |
|---|---|---|
| Submit — ожидание linger | 6.33 мс | 30% |
| Submit — round-trip TigerBeetle | 10.57 мс | 51% |
| emit.Results (`ProduceSync`) | 1.74 мс | 8% |
| офсеты/коммит/poll (остаток) | ~2.24 мс | 11% |
| декодинг | 5.5 мкс | ~0% |

**Средний размер батча — ровно 1.0.** Потолок TigerBeetle на полном батче 8189 — 6.13 мкс/событие, то есть ~163k событий/сек. Оба главных расхода — симптом одного: синк обрабатывает запись, ждёт её исход и только потом берёт следующую, поэтому в очереди батчера никогда не бывает второй команды и `linger` истекает вхолостую.

**Architecture:** Синк перестаёт ждать каждый исход по очереди. Он ставит все записи опроса в батчер не блокируясь, затем собирает исходы в порядке постановки. Порядок применения внутри партиции сохраняется, потому что батчер применяет команды в порядке постановки в очередь, а записи одной партиции ставит одна горутина. Партиции обрабатываются параллельно.

**Tech Stack:** без новых зависимостей.

## Global Constraints

- Модуль `github.com/Mi7teR/kafka-tb`, Go 1.25+, `CGO_ENABLED=1`.
- **macOS:** только через `make` — Makefile подставляет `-ldflags=-extldflags=-Wl,-ld_classic`. Голый `go test ./...` падает на линковке.
- Порядок применения внутри партиции Kafka обязан сохраниться. Между партициями порядок не гарантируется и никогда не гарантировался.
- Офсет коммитится только непрерывным префиксом и только после того, как TigerBeetle подтвердил операцию **и** запись в DLQ/results подтверждена брокером.
- Ни один существующий инвариант из `internal/sink/offsets.go` и `internal/tbx/batcher.go` не ослабляется. Все текущие тесты обязаны остаться зелёными без правок семантики.
- `make test`, `make integration`, `golangci-lint run` — зелёные на каждом коммите.
- Conventional Commits.

### Task 14: Batcher.SubmitAsync

**Files:**
- Modify: `internal/tbx/batcher.go`
- Test: `internal/tbx/batcher_test.go`

**Interfaces:**
- Produces: `(*Batcher).SubmitAsync(ctx context.Context, cmd *model.Command) (<-chan SubmitResult, error)` — ставит команду в очередь и возвращает канал, в который придёт ровно один исход. Экспортируемый тип `SubmitResult{Outcomes []Outcome; Err error}` (сейчас `submitResult` приватный).
- `Submit` остаётся как есть и реализуется поверх `SubmitAsync`, чтобы не было двух путей постановки в очередь.

**Требования:**
- `SubmitAsync` возвращает ошибку немедленно в тех же случаях, что и `Submit` сегодня: пустая команда, `ErrCommandTooLarge`, батчер остановлен (`ErrClosed`), отменённый контекст.
- Блокировка при полной очереди сохраняется — это backpressure, и он нужен: без него синк поставит в очередь весь опрос и съест память.
- Канал буферизован на 1, писатель ровно один. Инвариант «каждая команда получает ровно один исход» не меняется.
- Вызывающий, который бросил канал не прочитав, не должен блокировать цикл батчера.
- Поведение при остановке: команда, поставленная так поздно, что её никто не увидит, получает `ErrClosed` — как сейчас. Не отвечать вовсе нельзя.

**Тесты:** порядок исходов при N параллельных `SubmitAsync` соответствует порядку постановки; заполнение очереди блокирует постановку; `Close` во время ожидания исхода отдаёт реальный исход, если батч уже применён (существующий инвариант); `-race -count=30`.

### Task 15: Пайплайнинг синка по партициям

**Files:**
- Modify: `internal/sink/sink.go`
- Test: `internal/sink/sink_test.go`

**Требования:**

- `processBatch` группирует записи опроса по `(topic, partition)` и обрабатывает группы **параллельно**, по горутине на партицию, дожидаясь их всех перед возвратом. `AllowRebalance` и `abandonBatch` остаются на горутине опроса — они не потокобезопасны относительно ребаланса.
- Внутри партиции: декодируем и ставим записи в батчер через `SubmitAsync` **в порядке офсетов, не дожидаясь исходов**, затем собираем исходы **в том же порядке** и для каждого делаем публикацию результатов, DLQ и `Done`. Порядок применения в TigerBeetle задаётся порядком постановки, порядок публикации исходов — порядком сбора.
- Число записей одной партиции в полёте ограничено конфигом (`sink.max_in_flight_per_partition`, дефолт разумный вроде 1000). Лимит нужен: без него отмена или сбой оставляет неограниченный хвост уже применённых, но не подтверждённых записей.
- Poison-записи не идут в батчер вообще — они получают DLQ и `Done` в порядке сбора, чтобы публикация исходов партиции осталась последовательной.
- Бюджет батча и путь `abandonBatch` сохраняются: по истечении бюджета партиции перестают ставить новое, уже поставленное дособирается, непроверенные записи откатываются через `SetOffsets` и `Forget`.
- Инфраструктурная ошибка на записи по-прежнему означает «не коммитим»: запись не помечается `Done`, а её партиция откатывается в конце опроса.

**Тесты:**
- Порядок применения внутри партиции сохранён при 500 записях (стаб-батчер записывает порядок постановки).
- Записи разных партиций реально идут параллельно (стаб с барьером: тест не пройдёт при последовательной обработке).
- Смесь poison и валидных в одной партиции: порядок публикации исходов соответствует порядку офсетов.
- Отмена контекста в середине опроса: ни одна запись не помечена `Done` без исхода, партиция откатана.
- Все существующие тесты пакета — без изменений семантики. `-race -count=30`.

### Task 16: Асинхронная публикация DLQ и results

**Files:**
- Modify: `internal/emit/emitter.go`, `internal/sink/sink.go`
- Test: `internal/emit/emitter_test.go`, `internal/sink/sink_test.go`

**Требования:**

- `ProduceSync` на горячем пути заменяется на асинхронную публикацию. Синхронный `ProduceSync` стоит 1.74 мс p50 на запись, асинхронная публикация тех же 3000 сообщений с одним `Flush` — 885 мкс суммарно.
- Контракт «офсет только после ack» **не ослабляется**: запись помечается `Done` только когда её публикация подтверждена. Реализация: публикация возвращает future/callback, синк собирает их и дожидается перед тем, как пометить записи `Done`, либо `Flush` перед коммитом с учётом ошибок по каждой записи.
- Ошибка публикации по конкретной записи — инфраструктурный класс: запись не помечается `Done`, партиция откатывается. Молча потерять запись в DLQ нельзя ни при каких обстоятельствах.
- `Flush` перед коммитом остаётся и обязан учитывать ошибки, а не только опустошение буфера.

**Тесты:** запись, чья публикация в results провалилась, не помечена `Done` и попадает в откат; провал одной публикации из пачки не мешает остальным; существующий тест контракта хедеров DLQ остаётся зелёным; `-race`.

## Фаза 2: пайплайнинг батчера

**Замеры после Task 16** (`.superpowers/sdd/perf-final.md`): 16 343 записи/сек, средний батч 428.7. Доминирует `CreateTransfers` — ~55% wall clock, ~33.6 мкс/событие против замеренных 6.13 мкс на полном батче. Причина: батчер держит **один запрос в полёте** на тип операции, поэтому пока запрос летит, следующий батч только копится.

Проверено по исходнику клиента (`tb_client.go`, `doRequest`): Go-клиент не сериализует вызовы — кладёт пакет в C-клиент и ждёт свой канал. C-клиент сам склеивает ожидающие пакеты в один запрос. Значит параллельные вызовы с нашей стороны дают выигрыш, а не блокируются друг о друга.

**Но порядок между параллельно отправленными пакетами не определён.** Просто поднять число воркеров нельзя: записи одной партиции Kafka разъедутся по разным запросам и применятся не в том порядке. Отсюда — привязка по ключу.

### Task 18: шардирование батчера по ключу порядка

**Files:** `internal/tbx/batcher.go`, `internal/model/command.go`, `internal/sink/sink.go`, `internal/api/write.go`, `internal/config/config.go`

**Требования:**

- У команды появляется **ключ порядка**. Синк ставит туда `topic/partition` — это ровно та единица, внутри которой порядок обязателен. API-запись ставит пустой ключ: два независимых HTTP-запроса не имеют между собой порядка и никогда не имели.
- Батчер держит `batcher.shards` независимых воркеров на каждый тип операции (дефолт 4). Команда попадает в воркер по хешу ключа. Пустой ключ — любой воркер (round-robin), чтобы API не сериализовался об одну партицию.
- **Инвариант, ради которого всё делается: две команды с одинаковым ключом никогда не находятся в полёте одновременно.** Один ключ → один воркер → один батч в полёте у этого воркера → порядок применения = порядок постановки. Между разными ключами порядок не гарантируется и не требуется.
- Все текущие инварианты батчера сохраняются пошардово: команда не режется между батчами, батч не длиннее `max_batch_size`, у последнего события каждой команды снят `linked`, каждая команда получает ровно один исход, инфраструктурная ошибка ретраит тот же батч.
- Протокол остановки (`stop` / `finished`, ожидание исхода по `finished`, а не по `stop`) распространяется на все шарды разом. `finished` закрывается после выхода **всех** воркеров.
- `max_queue` и `max_in_flight_per_partition` перечитать: очередь теперь на шард, а не общая. Валидация конфига должна отражать реальный смысл, а не старый.

**Тесты:**
- Команды с одинаковым ключом применяются строго в порядке постановки при 500 командах и включённом шардировании (стаб-клиент фиксирует порядок).
- Команды с разными ключами реально уходят в разные запросы параллельно (стаб с барьером: тест не пройдёт при одном воркере).
- Существующие property-тесты упаковки и все тесты остановки — зелёные без ослабления, прогон `-race -count=30`.
- Тест, который падает при отключении привязки: одинаковый ключ разложен по двум шардам → нарушенный порядок пойман.
